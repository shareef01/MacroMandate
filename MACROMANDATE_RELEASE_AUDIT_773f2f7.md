## A. Executive summary

**Verdict: MVP. Hold a general production release.** The Android app delivers a complete manual meal log and a usable optional photo path, with editable estimates, trends, reminders, a widget, and user-initiated exports. The signed release is real, CI exercises builds and instrumentation, and the repository already contains meaningful defensive controls. The strongest are provider-specific credential storage, HTTPS enforcement, EXIF-free uploads, canonical filesystem containment, a timestamp index, and a tested Room 6→7 upgrade.

Three data guarantees fail at the implementation boundary. Restore replaces an existing meal even when the archived copy is older or missing the current photo. Photo saves and reconciliation do not share an ownership or commit protocol, so a valid database record can outlive its image. Erase can delete photos after a failed database clear. An unrelated AI JSON object can also become a zero-calorie review draft. Fix these before a wider rollout. No Critical vulnerability was confirmed. The primary release risk is loss of user data under expected user actions and recoverable failures.

## D. Functional and reliability defects

**D1 · High · Confirmed by isolated SQL execution and source integration. Restore replaces newer edits and can remove photo associations.** Back up a meal, edit it, then restore the older archive. `ControlPanelScreen.kt:167–218` confirms a generic update policy. `MainViewModel.kt:481–496` immediately restores the parser's output. `BackupManager.kt:121–126` batch-inserts via Room `REPLACE` at `MealDao.kt:16–17`. Identity is the only conflict check. In an in-memory SQLite fixture using the committed schema and KSP-generated Room SQL, replacing an existing meal with its archived ID changed the name and calories and nulled its image URI. The user is warned that matching IDs update, but sees no actual conflict list. `DossierExporter.kt:154–165` also deduplicates legacy entries first-wins on a 32-bit hash of timestamp/name/calories, omitting macros and other discriminators. A true duplicate and two distinct rows with the same fingerprint cannot be separated. [Restore DAO](https://github.com/shareef01/MacroMandate/blob/773f2f74bc869f2cd42959cc35f5e72924503a78/app/src/main/java/com/sharek/macromandate/data/local/MealDao.kt#L13-L29)

**D2 · High · Source-confirmed sequencing, device interleavings unmeasured. Photo saves and cleanup race.** Camera writes in the final evidence directory before analysis (`CameraCaptureScreen.kt:250–270`). Gallery confirmation publishes a copied file before committing its row (`MainViewModel.kt:561–613`, `EvidenceStore.kt:80–123`). Startup snapshots database URIs separately from the filesystem sweep (`MainViewModel.kt:116–120`, `EvidenceStore.kt:155–168`). Pause the sweep after the snapshot and publish a photo before resuming it. The new file is absent from the old snapshot and can be deleted despite an in-flight or completed insert. There is no mutex, age cutoff, or staging namespace. File publication is atomic within the filesystem, while the database and filesystem still commit separately.

**D3 · High · Source-confirmed cancellation windows.** If photo persistence completes on IO as the caller is cancelled, the result may never reach `storedUri`. If cancellation reaches the broad catch after assignment, the cleanup switches to IO in the already-cancelled context. A committed Room row can also coexist with a pending capture whose cleanup runs in `onCleared()` (`MainViewModel.kt:599–613,739–745`). This is especially important for camera captures because `EvidenceStore.persist` returns the original file and reports `newlyCreated=false` at lines 81–84, a flag the ViewModel ignores. On an ordinary insert failure, rollback can therefore delete the source needed for Retry. Cancel or fail immediately before file return, after file return, or after database commit to distinguish these outcomes. The correction needs stable identity, distinct staging ownership, and restart recovery. A cancellation catch or an unconditional file delete is insufficient.

**D4 · High · Confirmed by isolated fault injection and source integration. Erase can break surviving records.** A database-clear exception produces `databaseCleared=false`, then `DataDeletionService.kt:44–58` still calls `clearAllEvidence`. A probe using compiled production code and fake storage recorded one file-clear call and `evidenceCleared=true` after a synthetic database failure. The real clear is transactional across meals and activity (`MainViewModel.kt:104–115`), so a failed transaction can leave every record while deleting the photos. For single delete, a file unlink failure occurs after record deletion, and a repeated delete reports success because the row and URI are gone (`DataDeletionService.kt:30–41`). Startup cleanup offers a best-effort retry but provides no durable failure ledger or user-visible retry status. If a save or activity write overlaps erase, it can recreate data or leave a missing photo. The UI confirmation independently limits ordinary simultaneous actions, while the storage operations provide no serialization.

**D5 · Medium · Source-confirmed. JSON portability is incomplete and asymmetrically bounded.** Exports contain local URIs and coordinates, with no image bytes (`DossierExporter.kt:65–93`). Import nulls a URI that is missing or outside the current app-private evidence store (`BackupManager.kt:99–112`, `DossierExporter.kt:167–181,254–259`). A clean install or second device can restore text without photos. The generic user-facing copy says “full database restoration” at `app/src/main/res/values/strings.xml:280`, while the more accurate notice at line 354 is unreachable from the active restore dialog. Export can emit more than the restore limits of 10 MiB and 50,000 rows. Invalid records can silently default to zeros and placeholder names, and scalar or duplicate entries can be skipped without the active UI reporting counts. Restore errors have a specific parser type, but the dialog checks a separate ViewModel type with no translation. Test an exported large data set, a second installation and documented invalid input.

**D6 · Medium · Source-confirmed. Lifecycle and errors can lose user work.** The active manual form closes before awaiting `SaveResult` and discards it (`MainScreen.kt:211–220`), so a storage failure leaves no usable error or retry draft. Dialog visibility, camera screen, filters and search are plain `remember` at lines 99–117. Pending analysis lives only in the ViewModel at `MainViewModel.kt:220–227`, so rotation can preserve the activity ViewModel while process death drops review state. Edit uses a saveable busy flag with a composition-owned coroutine (`MealDetailScreen.kt:365–370,424–448`), risking restored “saving” state after its job has disappeared. Camera setup blocks on a future in disposal and runs a late listener without fencing its lifetime (`CameraCaptureScreen.kt:108–132`). Some failures are log-only, and camera permission denial does not yield a clear fallback message at `MainScreen.kt:138–145`. Verify rapid camera back/rotate, denial, and a permission loss during capture.

**D7 · Medium · Source-confirmed legacy gap with bounded exposure.** `AppDatabase.kt:29–69` only registers 6→7. Version 1 is present in repository history, and versions 1–5 have no committed schema fixtures. Release preserves unsupported files but fails to open them. Debug can destructively recreate them. All four published tags use schema 7, so the normal tagged update path is distinct from unsupported historical builds. Database opening is lazy and the UI flows lack a migration-specific recovery surface. Restrict the support promise to verified upgrade paths and preserve/export data for any additional historical release actually supported. [Database source](https://github.com/shareef01/MacroMandate/blob/773f2f74bc869f2cd42959cc35f5e72924503a78/app/src/main/java/com/sharek/macromandate/data/local/AppDatabase.kt#L29-L73)

**D8 · Medium · Mixed confidence. Time windows and background behavior.** `MealDao.kt:34–38` applies only a lower bound. A clock correction can put a later-day row into Today and Trends SQL selections. `MainScreen.kt:175–209` computes the Today history filter inside a remember block that omits the date boundary, so the history filter can stay stale across midnight while Today totals roll over. `MealRepository.kt:90–118` uses calendar-day arithmetic and periodic recomputation. The timezone/DST device matrix is unverified. `MandateApplication.kt:23` reschedules unique widget work with `REPLACE`, and the running worker also schedules its successor with that policy (`MidnightWidgetRefreshWorker.kt:24–38,61–72`). A startup immediately after midnight can displace overdue work. The widget has a 30-minute platform update interval as a fallback, with approximate timing. Settings requests Android 13+ notification permission on enable and displays a blocked state (`ControlPanelScreen.kt:398–430,1119–1136`). That state checks app-wide access, not the individual reminder channel. The permission UI and actual delivery still need an end-to-end matrix under Doze and revocation.

**D9 · Medium · Confirmed APK metadata. Optional hardware can filter store distribution.** `app/src/main/AndroidManifest.xml:5–20` declares `camera.any` optional, but APK badging for both the published and locally built release lists implied back-camera and location features. Google Play interprets some permission-implied features as filtering criteria. Manual logging does not require either sensor. This is a Play catalog compatibility issue. GitHub sideload installation and the actual unpublished Play device catalog were not tested. [Android permission-implied features](https://developer.android.com/guide/topics/manifest/uses-feature-element)

## E. AI integration assessment

**Provider consistency.** The default `https://openrouter.ai/api/` + `openrouter/free` in `app/build.gradle.kts:62–84` aligns with README onboarding, Settings labels from `ApiConfig.providerName`, and the relative `v1/chat/completions` path in `network/HuggingFaceApi.kt:9–15`. `network/ApiConfig.kt:28–52` scopes keys to a normalized endpoint, limits recognized HF and OpenRouter prefixes to their configured destinations, and always builds a bearer header. The earlier hypothesis of a default provider mismatch does not hold at this revision. Legacy HF and compatible proxy endpoints are build-time overrides. Existing HF keys do not become OpenRouter keys. A key passing the prefix check may still be expired, invalid, or out of credit. Settings saves locally without a server handshake, which the wording “saved” accurately describes. Document that the first request checks authentication and model access.

**Transfer and logging.** `MealAnalysisCoordinator.kt:34–91` reads private preferences and optionally looks up a fresh location with a five-second wait. The separate send toggle governs whether coordinates are burned into the uploaded pixels. `ImageForensics.kt:50–145` honors image orientation and re-encodes to a JPEG with an edge of at most 800 pixels at the coordinator's settings. Source EXIF is dropped from the request, while the locally saved original may retain it. The provider still sees everything visible in the image. `MainViewModel.kt:252–325` sends structured JSON containing today's meal names, calories, macros and liquid flags, plus totals. Prompt instructions treat images, OCR and meal names as untrusted. The client renders returned text without executing it. These instructions are a useful quality control with model-dependent effectiveness. Third-party transfer including indirect routing, account-level choices, retention and local deletion limits should be disclosed together before use. [Free Models Router](https://openrouter.ai/openrouter/free) · [OpenRouter provider policies](https://openrouter.ai/docs/guides/routing/provider-selection)

**E1 · Medium · Confirmed by isolated execution and source integration.** `NutritionAnalyzer.kt:69–95,104–135` returns the first candidate that `NutritionSanitizer.kt:37–92` parses. Missing or unusable fields default to values even when no nutritional fields exist. Compiled audited code accepted `{}` and `{"status":"unavailable"}` as “Unidentified item,” zero kcal, zero macros. It rejected non-JSON at the sanitizer and flagged a 1 kcal/100 g protein contradiction. An empty transport choice is already rejected by the analyzer tests. The missing distinction is between legitimate explicit zero nutrition and a syntactically valid but semantically empty response. Review and correction are mandatory before persistence, which reduces the impact. Daily summary has a parallel issue where a successful HTTP response with blank/missing content creates an empty successful briefing (`MainViewModel.kt:285–296`).

**E2 · Medium · Documented and source-confirmed nondeterminism.** OpenRouter says its free router randomly selects compatible free models. The app sends a model ID and a 600-token completion cap, and consumes only the first choice. It neither requests a schema nor tracks the served model, and it provides no explicit application-side fallback. It disables connection retries and maps 401/403, 402, 429 and other status families into user-facing errors. Connect/write/read/call limits are 15/30/60/90 seconds, plus preprocessing. There is no `Retry-After` handling, response-size limit, controlled repeatability, or quality benchmark. Status messages should preserve user work and distinguish rate, transport and invalid content. A controlled model or explicitly tested routing policy can retain manual logging and review without surprise retries, costs or broader data transfer. [OpenRouter routing behavior](https://openrouter.ai/openrouter/free)

**E3 · Medium · Source-confirmed shared state.** Analysis and briefing have separate Jobs but write the same loading/error state (`MainViewModel.kt:240–265,285–299,514–547`). New briefing calls overwrite the Job reference without cancelling the existing request. Replacing an image job uses shared capture state across asynchronous completion, and a new successful estimate replaces the previous pending state. Test late results, repeated taps and cancellation across tabs. A photo provides approximate portions, hidden ingredients and no validated nutrition ground truth. Evaluate an opt-in labeled meal corpus for supported models and keep the editable estimate warning.

Prior-audit corrections follow from the executable paths. `docs/AUDIT_REPORT.md` finding A-23 describes the unbounded history flow as export-only, but Dashboard and Detail subscribe to it. `docs/PLAY_RELEASE_CHECKLIST.md` mentions Hugging Face as the default and says there is no native code. The audited configuration uses OpenRouter and both release APKs contained four native libraries per ABI. `docs/PRIVACY_THREAT_MODEL.md:55,172,254,278,286,306` also misstates camera staging, the condition for location transfer, the backup cap, HTTPS enforcement, startup sweeping, and summary data sharing. Update the active privacy document and keep the historical reports dated.

## F. Performance assessment

- **Confirmed unbounded data path, unmeasured latency.** `MealDao.kt:25–38` and `MealRepository.kt:39–47` materialize every meal. Dashboard applies search, filtering and sorting in composition at `MainScreen.kt:175–209`. Lazy rows save view work but cannot reduce database transfers. Detail loads the entire list for an ID and weekly report loads all history before filtering. Push filters/ranges and stable secondary ordering into SQL, use bounded paging and row-by-ID detail, and benchmark long histories.
- **Backup and startup memory.** `BackupManager.kt:18–43,60–83` holds full snapshots and encoded copies. JSON export constructs the whole object tree, string and UTF-8 bytes. Startup reads whole meals and enumerates files. Query just referenced paths, move reconciliation to serialized maintenance, and stream bounded exports through a snapshot consistent with the archive format.
- **Images and low-end devices.** `ImageForensics.kt:25–36,50–91,120–145,153–209` samples, rotates, optionally watermarks, then scales and encodes. Power-of-two sampling is approximate. Multiple decoded bitmaps, buffers and base64 text can coexist. EXIF and gallery stream reopening can be slow, and a blocking location task occupies IO until its timeout. Persisted gallery bytes have a 15 MiB limit. Camera direct-write reuse bypasses that copy limit. Reject or normalize oversized sources earlier and measure peak heap on portrait, landscape and extreme aspect ratios.
- **Battery and accessibility.** Reminder work is periodic and battery-aware. The camera has an animation reduction setting and disposes bound use cases on navigation when setup has completed. Trends provides chart and map semantics (`AnalyticsScreen.kt:545–557,698–721,877–899`), but those descriptions do not verify TalkBack focus flow, large-font layouts, touch targets, color contrast, RTL or permission UX. Measure with a low-memory device, large text, rotation and reduced motion. No frame, heap, startup or battery benchmark was run.

## J. Final engineering verdict

**MVP.** There is enough here for controlled testing and feedback, with functioning manual entry and a real distribution pipeline. The present branch falls short of beta-ready for an audience relying on the log as their only copy. After the P1 items pass isolated failure-injection and upgrade regressions, the P2 device and performance matrix can establish the case for a production release. Production hardening would additionally require repeatable dependency checks, evidence recovery under process death and filesystem failure, and verified AI data-handling and model quality.
